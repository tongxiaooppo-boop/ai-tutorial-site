第 23 天｜卡關處理

先修：第 18 天（卡關時隨時翻）分 4 條路線，選一條走

第 7 天｜卡關：說清楚錯誤，檢查 AI 改了什麼

白話觀念卡

「不能用」是感受；「輸入 100，按換算後沒反應，Console 出現某段錯誤」才是能查的線索。回報時要交代環境、操作順序、預期結果、實際結果及原始錯誤文字。

diff 是修改前後的對照。刪除與新增通常用不同顏色標示，但顏色不代表好壞。你要檢查的是：改動是否解決問題、是否順便改了其他規則。

每次先保存正常版本，一次處理一個問題。AI 說修好了，仍要用原本失敗的操作再測一次。

示範工具

  • 首選：Gemini 免費版。貼上去識別化錯誤、相關程式與 diff，就能討論原因，不需要開放本機權限。
  • ChatGPT：適合解釋錯誤與比較修改；有資格使用 Codex 時，可直接在專案中閱讀與修改。
  • Claude：可分析相同資料；有 Claude Code 資格時，能在 VS Code 檢視提議差異，仍須人工驗收。

步驟

  1. 打開作品，先保存正常版本。記錄瀏覽器、開啟位置、操作順序、輸入值、預期與實際結果。
  2. 依下方提示詞提供錯誤原文與相關程式，先移除秘密及私人路徑，請 AI 提出最小檢查，不一次重寫整份作品。
  3. 比較前後修改，檢查公式、資料來源、外部連線、輸入規則及額外檔案。
  4. 重測原失敗案例及 100、0、空白、負數；資料模式另測有效 JSON、空檔與錯誤格式。
  5. 練習還原前先另存想保留的內容，還原後重測；不要清空整個工作區。

路線①：網頁版

在 GitHub 開啟檔案的 History 查看前次版本與修改差異；網頁 Revert 官方流程只針對已合併 PR，不保證任意 commit 有一鍵還原。練習時開啟正常舊版、複製完整內容，回目前 index.html 的編輯器手動貼回，核對後以新 commit 保存。開啟更新後作品重測，已開 Pages 就等重新部署。

路線②：桌面 App

在 GitHub Desktop 的 Changes 選檔看 diff。未提交的失敗修改可對該檔使用 Discard Changes，先確認會移除哪些內容；已提交則在 History 對錯誤 commit 按右鍵 → Revert Changes in Commit，新增反向 commit，再 Push origin。多筆還原可能衝突，先從單筆練習；不要丟棄仍想保留的內容。

路線③：VS Code

在 VS Code Source Control 點選 index.html 看前後差異，或執行：

git status
git diff --stat
git diff -- index.html
git diff --cached

未暫存與已暫存內容分開看；新檔也要直接開啟。未提交的失敗修改可對該檔 Discard Changes，先保留副本；已提交的錯誤請老師帶領用 git revert 建立反向提交，再重測、推送。不用 reset --hard 或 git clean 清空專案。

路線④：本地小作品

並排打開 fx-v1.html、fx-v2.html 的原始碼，比較與問題相關的部分；不要只看 AI 摘要。新版失敗時先保留作除錯紀錄，重新開啟正常舊版驗收，再以新檔名繼續修改；不覆寫唯一正常副本。

範例提示詞

請協助我除錯，先依證據縮小問題範圍，再提出最小修改。
不要先重寫整份網頁。

<環境>
Windows；工具路線：【①網頁版／②桌面App／③VS Code／④本地小作品】。
瀏覽器：【填Chrome或Edge及版本】。
執行位置：【本機檔案／本機網站／GitHub Pages】。
作品：單一index.html匯率換算器。
</環境>

<重現步驟>
1. 開啟換算器。
2. 選擇固定練習模式，匯率1 USD＝32 TWD。
3. 輸入100。
4. 按「換算」。
</重現步驟>

<預期與實際>
預期：3,200.00 TWD。
實際：【填畫面真正發生的事】。
最近一次修改：【填修改項目；不知道就寫不知道】。
</預期與實際>

<錯誤原文>
【貼上Console或終端機的完整錯誤，保留檔名與行號；
先移除秘密、私人路徑與個資。沒有錯誤就寫沒有觀察到。】
</錯誤原文>

<相關程式或diff>
【貼上相關內容；不確定範圍時先說明，不要捏造程式。】
</相關程式或diff>

請依序輸出：
1. 已知事實。
2. 最多三個可能原因，區分推測與有證據支持的原因。
3. 下一個最小檢查動作，以及不同結果各代表什麼。
4. 證據足夠後的最小修改，標明檔案與修改前後內容。
5. 如何重測原問題，以及哪些既有功能也要重測。

不要讀取.env、關閉安全限制或加入陌生轉送服務。
若缺資料，指出要補哪一段，不要宣稱已測試或已修好。

驗收

  • 是／否：另一個人只看回報，就能重做相同操作？
  • 是／否：能指出 diff 中至少一項修改的目的？
  • 是／否：原問題與基本案例重測通過，而且知道如何回到存檔點？

正常範例

輸入：「練習模式輸入 100，按換算後沒反應；Console 顯示 ReferenceError: convertCurrency is not defined。」

預期：AI 先檢查按鈕呼叫名稱與函式定義是否一致，依實際程式提出修改；修改後按鈕正常，結果為 3,200.00 TWD。

失敗範例

AI 回答：「已全面優化。」diff 卻顯示幾乎整份檔案被替換，還新增外部套件與資料來源。

辨識方式：無法把大量改動對應到原本錯誤。先停止接受，要求縮小修改；必要時回到正常存檔點。

常見錯誤
  • 只貼截圖說「壞了」，沒有操作順序、輸入值與錯誤原文。
  • 把 Failed to fetch 一律當成 CORS；也可能是網路、網址、服務或其他原因。
  • 只讀 AI 摘要，沒有看實際 diff，漏掉公式或資料來源被更換。
  • 長對話開始混入舊規格，仍繼續要求修改；可整理目前規格、錯誤與已試方法，再開新對話。
  • 為了還原直接使用 git reset --hard、git clean，或把完整日誌連同金鑰一起貼給 AI。
